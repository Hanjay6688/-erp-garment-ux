# Race blocker review

## `external/xaudit_3.py` read

- `side()` opens `boundary.ADMIN` (fallback `boundary.PG`) and then calls `api.admin(k)`; all three cases call `side()` before the race. The fixture side connection commits, then fresh side connections race and commit. This is incompatible with any audit boundary requiring the whole scenario to stay inside a primary connection/savepoint.
- `race()` constructs the side connection **before** its `try` block. A connection/setup exception escapes the thread and leaves `out[i] = None`; even after successful setup, a worker still alive after `join(timeout=120)` leaves an absent result. No explicit failure oracle for either situation.
- Import oracle `posted[0] <= 1` counts POSTED items only for a location across the fixture and race; it does not require both workers to have executed or prove product refusal.
- Close oracle `filings is None or filings <= 1` and `ok <= 1` can mark PASS with no filing, no successful close, or missing worker results. It obtains `current_setting('app.closed_through', true)` without validating it.
- WIP oracle does require exactly one recorded worker success, but needs explicit worker completion and SQLSTATE/product refusal checks to discriminate permissions/setup failures.

## `cp6_aw_probe.py` helpers and oracle assessment

- `race_setup(admin, today, verify)` verifies the installed runtime on an admin connection, rolls that transaction back, then grants `USAGE on schema erp to authenticated`, conditionally `api.seed(cur)`, and commits in a **separate race database**. `fresh_race_copy` drops/recreates `cp6_aw_race` from `cp6_rollback` for each schedule. `two_sessions` has a holder and worker with bounded lock/statement timeouts and measures blocking with `pg_blocking_pids`. `close` interprets a SQL refusal via `r1.peer.attempt`; `control` reads `erp.accounting_period_control.closed_through` and the filing count. `quiet_seed` clears due attendance/payroll blockers for date readiness; call it only in the isolated race copy, and preserve its result as fixture evidence.
- `xaudit_3.race_close` does **not** arrange preflight READY. If it is BLOCKED, the legitimate outcome is two refusals and zero filings. Its own prose allows this, but the current checks do not require two product-level close refusals, unchanged filing/control, or evidence that both threads actually attempted the call. If READY, require exactly one committed filing for `closed_through = d`, exactly one successful close, a semantic refusal for the other, and the expected control row. A `to_regclass` missing-table result is INCOMPLETE, never PASS. `current_setting('app.closed_through')` reads a session setting on a new connection and is not the persisted close-control oracle; replace with `erp.accounting_period_control`.
- Import should count the exact `(material_id, location_id)` opening item and unique racing batch IDs, assert the initial header is posted, preflight two staged batches before releasing a barrier at FINALIZE, then require both worker outcomes (one may return DRAFT/refusal), exactly one posted item total for that key, and no duplicate ledger impact. Current `second_batch` creates/uploads/finalizes inside the barrier race and `n_posted` parses `str(r)`; this neither guarantees overlapping finalizations nor authenticates the product result.
- WIP should require both worker attempts, one success and a specific stale-version refusal from the other, then verify exact output count/quantity and remaining source state. Current Python `int(float(outputs[1])) <= 8` loses decimal precision; compare `Decimal` quantities. Distinguish setup/timeouts/permission failures as INCOMPLETE, never a legitimate race refusal.

## Minimum supported change and rerun recipe (prepared, not executed)

The existing `AUDITOR_SCENARIO` interface (`cases(cur,today)`) offers only the main savepoint connection. An external script cannot make committed fixtures visible to side sessions without violating the case isolation of that interface. The minimum safe runtime change belongs in an **audit-only runner mode**, patterned on `cp6_au_r1_probe.py:races` / `cp6_aw_probe.py:fresh_race_copy`, separate from `r1.group`:

1. Finish/install the committed candidate on `cp6_rollback`, verify the exact candidate function pins and record head/tree/source hashes. Create a uniquely named disposable race database from that clone via `createdb -T cp6_rollback`, while no open source transaction interferes; take an initial state fingerprint of the source clone and primary.
2. Build an admin URL by replacing only the database name in the known runtime `boundary.ADMIN` connection string (no credentials in logs). Connect to the new race DB; verify its installed runtime. Commit the schema `USAGE` grant and conditional foundation seed/OWNER actor mapping (`api.seed` if `erp.app_users` empty), and the open-period setup needed for fixtures. In a fresh connection, preflight `has_schema_privilege('authenticated','erp','USAGE')`, authenticated `session_user/current_user`, JWT `sub`, `erp.current_app_role() = 'OWNER'`, and a harmless owner-only workspace call. Fail INCOMPLETE before starting any race if any check fails.
3. Make **one fresh race copy per schedule/case**, commit only its fixture in that copy, and assert its readiness: initial posted balance and exact item key; two staged import batches ready for FINALIZE; close preflight status READY (after explicit quiet seed) or explicitly BLOCKED with cited blockers; WIP source remaining and output count before the two calls. Start two connections using the copy's admin URL, set bounded `lock_timeout`/`statement_timeout`, and synchronize immediately before the target action. Record both backend PIDs, started/completed state, SQLSTATE/primary error, product return JSON, and post-state. Roll back/close on error and join or cancel all workers before copy deletion.
4. Oracles fail closed on missing worker outcome, timeout, setup/permission failure, unexpected status, or missing schema/table. Require the exact initial/final data and one product-level refusal (specific reason where defined). A close READY case requires exactly one filing and control at `d`; a BLOCKED control requires zero filings and two semantic refusals. Keep result labels separate from job colour.
5. Always drop the race copy in `finally` with the existing Docker-local `supabase_db_cp5-local` guard. Assert `race_database_remaining=0`, source clone unchanged, primary unchanged, and function definitions/ACLs unchanged. The normal runner then still drops `cp6_rollback` and asserts primary unchanged. Do not commit to the main scenario savepoint, send SQL to hosted/legacy/production targets, or modify installed product definitions.

This is a design proposal, not a validated patch. No disposable database or native rerun was launched in this review; there is no proven concurrency result from the two xaudit_3 runs. Reuse existing approved AR/AT/AU audit-only helper runtime for the implementation and rerun under its clone guards.

**Runner placement:** invoke the race-only hook **after** `r1.group(...)` has closed and rolled back its main connection, and **before** `cp6_auditor_scenario.run`'s `finally` drops `cp6_rollback`. Do not launch `createdb -T cp6_rollback` within `module.cases` or its active savepoint. A race hook can be a second callable (`race_cases(race_context)`) with a separately reported status/counts and a separate disposable database per case; keep the ordinary `cases` interface unchanged. Treat unimplemented hook as no race evidence, not PASS.

## Feasibility determination after inspecting helper calls

`awp.fresh_race_copy(admin, verify)` is **not callable safely inside `xaudit_3.cases()`**. Its implementation first drops `awp.RACE_DB`, then calls `r1.docker('createdb', ..., '-T', 'cp6_rollback', awp.RACE_DB)`, then `awp.race_setup(admin, None, verify)`. `r1.group` invokes `cases()` and every operation while its admin connection to source `cp6_rollback` remains open. Copying a PostgreSQL database as template while that source connection is active violates the template's no-active-connection requirement. Changing `awp.RACE_DB` global would also collide with helper ownership/state. `awp.race_setup` itself is safe only when called against a separately created disposable race copy: it verifies/rolls back, commits schema USAGE and conditional `api.seed`. That grant is an **expanded audit fixture ACL**, not a proof of original production ACL. There is no race hook in `cp6_auditor_scenario.run` after `r1.group`; thus a standalone replacement `xaudit_3.py` cannot safely schedule committed two-session races through this dispatch path. A hook/integration patch is necessary; do not monkeypatch the runner or commit `cp6_rollback` from the external scenario.

**Exact hook contract:** `module.race_cases(race_context)` would run after `r1.group(...)` returns and its connection closes, before `finally` drops `cp6_rollback`. `race_context` contains read-only `candidate_head`, `verify`, `source_clone='cp6_rollback'`, `primary_snapshot`, and authorized local container name. It should reject any URL/database mismatch and use its own unique race DB name per case (e.g. `cp6_xaudit3_import`, `cp6_xaudit3_close`, `cp6_xaudit3_wip`). For each case: `dropdb --if-exists --force` of only that exact race name; `createdb -T cp6_rollback`; derive admin URL preserving connection options; `awp.race_setup(admin, None, verify)`; verify actor/grant; commit relevant setup and fixture; execute/assess both sessions; drop exact race DB in `finally`; verify absence and source/primary fingerprints. All exceptions become INCOMPLETE with a stage label. Runner prints `auditor_race_cases` separately, and sets overall INCOMPLETE if setup/worker/cleanup fails. The check of original ACL remains sourced only from the original runtime; the modified copy is marked `fixture_expanded_schema_usage=true`.

**Import oracle correction:** Given an already POSTED initial opening item at the exact key, the intended safe result is **zero** additionally posted racing batches, not one. Prepare both second batches to a valid READY-to-FINALIZE state, commit, then race only FINALIZE; require two completed authenticated OWNER workers, two duplicate-overlap refusals (or documented nonposting DRAFT responses with reason), one posted opening item total for exact material/location key, unchanged ledger quantity from the pre-race fixture, and both second batch statuses non-POSTED. If the product intentionally permits one second batch under a different key, that is a different test and must be specified separately.

**Close oracle correction:** Define READY schedule after `awp.quiet_seed` or another explicit readiness fixture, with observed preflight READY, zero same-date filings, open control before race. Require one successful close, one close-specific refusal, one same-date immutable filing, and control advanced to `d`. A separate BLOCKED control can require both close-specific refusals, zero filings, unchanged control. Error `42501`/permission, missing worker, missing table, timeout, and connection setup are INCOMPLETE, even when `count <= 1`.
