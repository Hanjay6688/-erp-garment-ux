# CP6 HTTP/Auth blocker review (source-only)

Scope: candidate `9add57ea8c2b6b2dc37c0134717d4d39ba30b5dc`, external audit snapshot `cf301a6f0c128ac8c221ab11e22c95db0ce1c896`. I inspected `external/xaudit_4.py` and candidate sources through read-only GitHub access. I did not execute the audit script, inspect Docker, obtain keys, run a workflow, or exercise the database. The reported `Credential Materialization` classifier rejection is in the external progress document, not independently observed in this session.

## What blocks XA4 and why it is insufficient even if dispatched elsewhere

`xaudit_4.py:start_rest` copies the entire live PostgREST container environment into an env file, returns `PGRST_JWT_SECRET`, and `jwt()` signs HS256 bearer tokens for anon/unmapped/seeded operator. That is credential extraction and materialization, the reported blocked operation. Re-running, repackaging, or moving this operation to a different dispatch interface would not resolve the substantive concern. Its own header says it does **not** exercise GoTrue login. Thus its result could prove only PostgREST behavior with manually signed claims, never the real Auth-login boundary required by GATE-04/08. `apikey` is set to the minted token too; the already established browser path instead uses an anon key for `apikey` and an Auth-issued token for `Authorization`.

The oracle is incomplete: XA4 covers anon/unmapped/operator only, with no inactive user or valid view-only role despite its header naming those states. It derives argument names from `pg_get_function_arguments` split on commas, which is unsafe for signatures with comma-bearing defaults/types, and fills UUID/date/JSON placeholders rather than valid domain fixtures. A 400/404 from argument resolution or business validation is not proof of an authorization refusal. `operator_reads_200` requires `preflight`, `pocket_workspace`, `import_workspace` to return 200 but does not validate response identity or semantics, and the matrix does not check full ERP data unchanged on refusals. It uses a hard-coded operator UUID without an independent positive resolution in the exact clone. Even a successful XA4 run should therefore be labeled partial PostgREST/claims evidence, not actual login or complete role coverage.

## Existing safe route in candidate sources

`scripts/cp6_t3_browser.py` already creates a separate PostgREST container pointed at `cp6_rollback` and invokes `scripts/cp6_au_browser_ui.mjs`. The latter creates disposable Auth users through GoTrue admin, obtains access tokens through `auth/v1/token?grant_type=password`, uses anon key as `apikey`, calls `http://127.0.0.1:54329/rpc/...` with the Auth-issued bearer, and signs an owner into the real candidate UI with Playwright. It masks secrets/JWTs in reported errors and deletes users on teardown. `scripts/cp6_t3_browser_verify.py` pins the release-package ledger and whole catalog on the clone. The T3 workflow starts a disposable database and destroys it afterward; its browser proof is explicitly labeled `T3_PREP` and 10 AU browser cases. These **are not** a CP6 ten-facade role matrix, and the existing job should not be cited as if they were.

`scripts/cp6_auth_permission_e2e.mjs` is a closer reusable pattern for the role matrix: disposable Auth users (owner, operator, viewer, inactive, unmapped), real password grant, expected HTTP statuses by role, active role IDs, denial controls, and Auth residue checks. `scripts/cp6_v2620an_access_revalidation.mjs` shows same-bearer revocation/remap, an all-ERP-table boundary digest around denials, and an explicit planned-case list. These source patterns predate the new ten facades and do not independently close this gate either.

## Concrete remediation specification for the writer's disposable T3 path

1. Add a distinct, source-pinned `T3_CP6_AUTH_FACADE_MATRIX` proof to the existing disposable T3 browser/HTTP flow. Reuse its already established GoTrue and PostgREST provision, anon key handling, real password-grant sessions, candidate catalog verification, and clone disposal. Never read `PGRST_JWT_SECRET`, sign JWTs, copy a container environment into a retained file, or persist credentials/tokens in evidence.
2. Before requests, resolve exactly one active OWNER and the actual role IDs/permission sets for view-only and other selected non-owner users in `erp.app_roles`/`erp.app_role_permissions`; create disposable Auth users and matching `erp.app_users` rows, including an inactive mapped user and a truly unmapped Auth user. Assert count and uniqueness of each identity and prove each Auth `sub` maps to the intended record. If a role/fixture is absent or ambiguous, return `INCOMPLETE` without replacing it with the owner's role or a synthetic claim. Keep setup mutations distinct from HTTP observations.
3. Use an explicit frozen manifest of ten facade names and exact JSON argument objects derived from the pinned function signatures and valid disposable fixture records; verify those signatures before testing. Do not infer arguments with string splitting or count malformed-input responses as access evidence. POST all ten via public PostgREST under anon, unmapped, inactive, owner, and representative existing roles. Add at least one real browser UI request through the same proxy for a CP6 page to prove browser→Auth→HTTP→facade; direct HTTP rows should be labeled as such.
4. Match refusals by HTTP status **and** structured PostgREST error `code`/message (`42501`, or the specific `P0001` owner guard, as pinned per facade). Differentiate `401/403` schema/function grants from `400` business errors; fail on unexpected `404`, parsing error, or successful writer response. On authorized reads assert 200, expected response shape/fixture identity, and change of outcome for the same facade under a different identity. For accessory workspace, use the actual `finance.contractor_accessory.view` permission: AUDITOR_VIEW_ONLY and KEUANGAN may read while `erp_save_accessory_issue_action_v1` requires create permission. The external audit's DB evidence already called an all-denied viewer oracle a counterexample to the oracle, not to product behavior.
5. Snapshot all relevant ERP tables (or a verified exhaustive digest) immediately before and after each denial, including idempotency/audit/ledger state; deny tests may not create business changes. Assert the exact planned tuple set `(facade, role, expectation)` equals the actual unique case IDs; any omitted row, cleanup failure, ambiguous identity, wrong runtime/catalog, or unexpected status must fail closed. Capture head SHA, run/job/attempt, package ledger/catalog pin, statuses/error codes, identity role labels, before/after digests, and cleanup result, but redact tokens, passwords, anon/service keys and response data that could contain them. Destroy the clone; verify transient Auth users are removed from GoTrue and no production/legacy target was contacted.

This is a writer-side harness addition and execution request, not a local product fix. The current session can provide source review and this design, but cannot claim native HTTP verification or an observed classifier workaround. To close GATE-04/08, a permitted owner/writer runtime must run the new real-Auth proof on the exact candidate, publish redacted case-level artifacts, and have an independent auditor assess them. The separate two-connection concurrency and rollback gates remain open.
