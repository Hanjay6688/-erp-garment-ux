## Contract interpretation and limitations

- M:43-46 requires latest draft details and control total agreement without posting the control row. M:138 keeps all opening route overlap as an explicit gate, and M:1043 says cross-batch document identity still needs contract/tests. The native duplicate import is thus a substantive gap against a no-double-counting opening oracle, but **the contract does not uniquely identify a physical source by `material_sku + location + cutover` alone**. Two independently verified physical sources of identical SKU/qty/date could be legitimate; this fixture intentionally re-declares the same generated tag and quantity without any second physical-source evidence. The run proves the candidate accepts an indistinguishable replay through a new batch and doubles the ledger; it does not prove every second same-key opening should always be rejected. Remedy needs explicit source/document identity or reconciliation rule and positive distinct-source control.
- M:369-371 requires cutover validity, checked remaining, and linked reversal, while M:3820 explicitly forbids backdating that corrupts quantity/value prefix. U02 has a fresh UUID, current remaining 8 after reversal, and a valid cutover/today date, so it demonstrates a missing *historical ordering* guard rather than stale-version or actor-denial behavior. The arithmetic is consistent: 8 opening in SEWING → −8 on 22 Sep → −8 on 24 Sep → +8 reversal on 25 Sep gives −8 on 24 Sep; PO GL 60−40−40 = −20 through 24 Sep, +40 = 20 on 25 Sep. Only this fixture and dates were tested.
- All three jobs are audit-scenario runs in a disposable clone; cases run inside rolled-back savepoints. `full_boundary_restored=true`, final `primary_unchanged=true`, clone_remaining=0. They do not establish deployed/hosted exposure or a persisted production state. `RUN_COMPLETE` means the runner completed, **not** product PASS. Public facade calls use `api.ordinary`/authenticated session and seeded OWNER identity; source fixtures include administrative setup/writer helper. No HTTP/JWT transport was exercised.
- Scenario files at report snapshot cf301a6 were independently content-hashed against the native log values: open_1 9086 bytes SHA-256 983a66f58524aeebb8f57826023ada76b2bb5757b80ed61680cca0c3cb125333; open_2 5913 bytes SHA-256 e8b84000396cc6e9ee27cdd49a50ea3d3806386a7b916e7868fc9b974709e9e0; xaudit_1 9124 bytes SHA-256 32a872e5ca4bfbae4a49ca05ca746454e2fc8d3c007c0e8bb10609f7b233d4a4. ## Bounded challenge: is the F1-12 identity oracle unconditional?

A targeted search across the three restored contracts found **no rule defining `material_sku`/`product_sku` + location + cutover date + quantity as a globally unique opening source**. M:938 explicitly keys partially paid party balances by document number and allows two distinct documents for the same party; M:843 explicitly normalizes a supplier receipt/header/line identity across batches. Those are source-specific identities, not a generic stock-opening key. M:1043 says cross-batch document identity still needs contract/tests, and M:138 requires overlap proof across old routes without specifying an all-stock deduplication key. `open_2.py` generates a new batch code and request UUID and repeats the same material/product tag/location/qty/cost/cutover, but carries no independent original physical-source ID tying both batches to one counted item. Its tag-scoped query isolates the native doubled numeric result but cannot adjudicate whether the second row was intentionally another source of 7 units. Consequently: **numeric second-posting behavior CONFIRMED; potential P1 double-counting risk material; unconditional “same item/source duplicated” defect and an exact same-key refusal rule UNVERIFIED/HOLD pending owner source-identity semantics and a positive two-distinct-source control.** This does not weaken the observed +15.75 movement or the separate import-vs-legacy guard gap.
