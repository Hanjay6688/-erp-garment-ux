# F1-17 / F1-15 source and native evidence review

Scope: exact candidate `9add57ea8c2b6b2dc37c0134717d4d39ba30b5dc`, external audit source snapshot `cf301a6f0c128ac8c221ab11e22c95db0ce1c896`. Read-only review; no fresh scenario run or environment mutation.

## Audit scenario source: `xaudit_1.py`

The correction scenario uses a dedicated material fixture through writer helpers (`cp6_az_probe.final_receipt`, `cut`), one received unit consumed by one cut, then creates a linked `material_purchase_cost_corrections` header and item and calls the native post plus recalc queue. It measures daily ledger deltas against a prefixture baseline and checks zero raw quantity, zero ending `MATERIAL_INVENTORY`, WIP equal to the corrected one-unit value rounded to two decimals, and no daily negative inventory. Two directions are separately registered: `10.005→10.014` and `10.014→10.005`. The direct insertion of the correction document is privileged fixture setup, whereas the posting/recalc is the business function under test; this is native DB evidence, not Auth/HTTP/browser evidence. The post attempt uses a savepoint, returning `INCOMPLETE` if it refuses. No committed writes are implied by merely reading this source.

The exact rounded expectation deserves scrutiny: Python `Decimal.quantize(Decimal('0.01'))` uses its context's half-even default, whereas PostgreSQL `round(numeric,2)` rounds halfway away from zero. For `10.014→10.005`, a strict Python decimal-rounding expectation is `10.00`; a PostgreSQL SQL-money expectation is `10.01`. Therefore a discrepancy of WIP `10.00` against the scenario's `10.00` should not be called an incorrect target; the stronger independent invariant is zero inventory *value* for zero physical quantity, reconciliation of the actually posted receipt/correction and cut, and daily value-prefix integrity. The upward case `10.014` rounds `10.01` in both schemes, so its nonzero inventory value and excess WIP do not depend on this tie rule.

## Audit scenario source: `xaudit_2.py`

The invoice scenario separately creates one `ESTIMATED` material purchase via native draft/post, cuts the unit, then finalizes an actual invoice through `erp.finalize_material_purchase_invoice_v2` and processes recalc. It uses the same baseline/daily valuation checks. This corroborates a second business path (late invoice rather than direct correction) but uses the same underlying recost consequence; it is not an independent re-run by this reviewer. Its `expected_wip` repeats the Python half-even tie caveat above. An invoice-down result with WIP `10.00` matching the scenario expectation does **not** clear a residual +`0.01` inventory value when qty is zero; that residual remains a valid conservation counterexample under either 10.00/10.01 policy.

For the selector, the scenario clones one existing delivery and all its delivery lines into 101 new delivery IDs: an old `SENT` delivery at today−200 days and 100 more recent `SENT` deliveries (today−1 day, spaced a minute). The original line IDs are replaced, so prior claims on original line IDs do not attach to the clones. It calls `public.erp_get_bs_resolution_workspace_v1('ACTIVE','ALL',null,null,50,0)` and checks `lookups.laundry_sources`; the old source's sum of sent qty is >0, but the test does not subtract claimed qty in its DB-side `old_claimable` calculation. Because cloned lines have fresh IDs and no cloned claims, this is a plausible genuinely claimable old source; check SQL eligibility and any hidden filter before treating it as proved. Also check whether these cloned deliveries meet all real producer invariants: the fixture directly inserts delivery/line rows rather than posting 101 transactions, so the claim is about selector behavior on accepted table state, not an end-to-end user-created sequence. Its `PASS`/`COUNTEREXAMPLE` decision uses old ID membership only; `lookups_count==100` and true claimability are recorded but not gating status. The native row should be evaluated as a conjunction of those checks, not status alone.

## Candidate source inspection

The installed CP5 BS workspace function (`supabase/migrations/20260903070932_erp_v2_6_19_cp5_bs_resolution_recovery.sql`, near 740–828) computes `laundry_sources.qty_claimable_pcs` as sent minus posted received minus non-rejected MISSING/STUCK claims, but limits deliveries by physical date to 100 *without requiring that computed capacity to be positive first*. Its receipt and settled-claim lookup families also have 100-row caps (their eligibility filters differ). The successor public facade in migration 19b calls that workspace and rewrites only `rows`, returning the original `lookups` unchanged. The UI's `CreateClaim` uses only `workspace.lookups.laundry_sources.filter(qty_claimable_pcs > 0)` as its STUCK/MISSING select options, with no search/paging for excluded delivery IDs. An old eligible delivery beyond the latest 100 cannot be chosen. This is a supported source defect independently of the 101-fixture quality; it extends to the receipt/settled-claim families as an architectural cap, but the native 101 run exercises only delivery sources.

The AZ release SQL computes an independent per-movement `round(qty_signed * (current_unit_cost − original_unit_cost), 2)` target (near lines 250–260), with journal events based on that rounded delta. Thus the reported one-cent discrepancy is mechanistically plausible when a direct correction or late invoice posts its own rounded total and a consumed movement is repriced separately. A repair should reconcile at the authoritative posting boundary and propagate a cent residual deterministically; simply widening numeric precision or changing the test's rounded target would not remove a posted one-cent inventory balance for zero quantity.

## Assessment and limits

**F1-17 is substantiated as a cent-level accounting/valuation defect on this exact candidate, in direct correction and late invoice paths, upward and downward.** Upward −0.01 stock value at zero qty plus WIP 10.02 (vs a 10.01 cent-rounded corrected unit) is the clearest policy-independent counterexample. Downward +0.01 stock value at zero qty is independently wrong even though WIP 10.00 matches the audit script's half-even target; avoid asserting that WIP 10.00 is itself a second independently established bug until official invoice/line rounding is pinned. The recost review should follow purchase value, issue value, journal legs and dated reporting through all consumers; this audit did not test Auth/browser or every material correction path.

**F1-15 is confirmed in source and materially corroborated by the native 101-delivery workspace output.** Its operational impact is selection in the BS claim form: the eligible old delivery is absent from the only available in-memory options, and the public facade preserves the cap. The fixture's old delivery is cloned through privileged SQL with an unusually old physical date; no actual claim was attempted and production-path validity of all 101 delivery documents was not proved. A repair acceptance case should use valid business-created source records or explicitly prove equivalent invariants, verify true net claimable qty for the old source, test the real UI/RPC selector with search/paging, and separately cover receipt/settled-claim families. The source-level cap remains a direct defect regardless of those fixture limits.
