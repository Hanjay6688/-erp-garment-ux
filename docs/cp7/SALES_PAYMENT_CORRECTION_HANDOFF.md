## Entry points and product behavior

`ConnectedSalesPage.tsx` owns `erp_cp7_correct_sales_payment_v1`. `SalesPaymentPanel.tsx` exposes **Edit pembayaran**, **Lihat perubahan pembayaran**, and the existing individual inverse. `SalesPaymentCorrectionPanel.tsx` reads `erp_cp7_get_sales_payment_correction_v1`, shows exact adjacent original/replacement sources, edits amount, physical WIB time, cash account, method, reference and notes, and requires a reason and a fresh explicit review. Restoring previous contents creates another reviewed correction with its own immutable link; it does not erase either earlier fact.

The backend reuses the existing private owning `PAYMENT_REVERSE` and `PAYMENT` actions in one database transaction. It checks the actual parent version and complete payment review token, rechecks current OWNER/ADMIN and the existing six permissions, serializes the Native source locks, and creates a replacement only after the original inverse succeeds. Original posted clock, amount, account and posting fact are retained. `replaces_payment_id` retains its Native cross-invoice reallocation meaning and is not repurposed. Ordinary cash/bank payments only: opening advances, imported advance payments, existing reallocation children, drafts and already reversed originals are excluded. No new owner age policy is invented.

The generated replacement number keeps a short original prefix and the full correction request UUID. The private immutable link carries the exact original/replacement/sale/actor/request/reason. The same actor, UUID, payload and expected version replay the stored outcome after current authority is checked. A changed intent with the same UUID is refused. Existing SALES recovery preserves the exact envelope after a committed reply is lost; there is no second call to the public generic sales writer from this correction flow.

The original Native inverse can use today's economic date. For a genuinely older payment, two Native journals relocate those exact inverse lines to the original economic date: `PAYMENT_CORRECTION_TIME_NEUTRAL` mirrors the inverse, and `PAYMENT_CORRECTION_EFFECTIVE` reapplies its exact lines and dimensions at the original economic date. They add no net whole-ledger effect. Native `post_journal` retains the closed-period/open-posting-date rule. The source resolver admits these kinds only through the actual immutable link and exact original payment/journal IDs. Client requests cannot supply journal IDs or ledger lines. Stock, sale items, HPP and revenue have no payment-correction mutation path.

Untouched physical time is transmitted with its original microseconds. An operator-edited time is interpreted as WIB. Amount/capacity checks use decimal strings and BigInt cents: replacement capacity is the old active payment plus the current remaining invoice balance. Backend Native guards are authoritative. Failed or stale reads retire verified facts; old replies and current session/permission changes cannot revive a writer.
