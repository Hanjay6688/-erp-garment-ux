# Sourced conversion costs alongside SKU moving-average pieces

Prepared only. No installer, database entry, accepted parent or workflow is
introduced here. The prior six-case candidate remains unchanged and its
adoption remains blocked until the full financial scope is qualified.

The exact current projection loses a later cost attached to a converted lot.
In the retained PostgreSQL 17 counterexample an unsold pool is worth 70; the
original Native cost reconciliation adds 2 to its book and propagated lot HPP,
but the new SKU target stays 70 and refuses the transaction. The complete model
rolls back. Its authority/material providers are explicit models, not ERP
acceptance. First evidence remains separate from any proposed repair.

Stock-piece lineage and additional-cost lineage have different quantities.
Base component units sum to the actual pool pieces, including reservations.
A conversion's own sourced-cost units describe ownership of its extra cost;
they do not create pieces. Those units exist even while the extra cost is zero,
so a later supplier invoice follows transfers and sales made before that invoice.
Each actual conversion allocation keeps its own cost source and PO attribution.
The signed price comes from the unchanged Native allocation-extra calculation,
not from a new user-supplied value or from the official target being checked.

The independent oracle models exact rational ownership, scoped cent targets,
FIFO-independent economic transfer, sales, partial returns, reversal and later
cost changes. It does not read or copy SQL output. It cannot provide business
acceptance or replace the Native permission, date, replay, dependency or bounded
recovery checks. A modeled recovery floor is an input representing the existing
Native guard; production must still call that guard with its current sources.

The implementation must capture both component maps at posting, retain every
original snapshot, propagate the same cost fractions through every consumer,
and validate the whole current target/book change. Adding an extra amount only
to the physical lot's present warehouse would fail after a sale or another
conversion. Replacing current targets with booked values would hide the defect.

The prepared SQL now adds four private immutable cost tables and eight private
helpers. Ten existing economic functions are derived reversibly from the exact
parent source, alongside the financial targets, sync closure and independent
credit proof. Cost units remain distinct from pieces; signed costs participate
in scoped cents, current HPP and the original posted snapshots. No Native cost
guard or target/book assertion is weakened.

The independent rational oracle passed 16 controls. The PG17.5 model passed 37
checks, including the original consumer/credit controls and six new sourced
cost cases. Its eight retained Native cost bodies remain byte-identical. The
original 70+2 refusal is repaired in that model, as are a later 2→3 invoice,
sale before/after cost, a full sale before the invoice, and partial returns with
intervening recost and another warehouse. All modeled tables are restored.
These are not actual ERP, Auth, browser, race, installation or acceptance cases.

Two first harness failures are retained separately: the old credit assertion
expected only three base roots, and the journal storage provider supported only
mapping keys. The successor checks the exact three roots plus the zero cost
root, and supports a validated explicit Native account ID. Monetary assertions
and the original target/book refusal remain unchanged.

Before actual qualification, integrate the exact SQL sources, metadata/ACL
fence, complete source graph and inverse. Cover accessory usage, late invoice,
mixed PO/non-PO ownership, descendants, partial-return cents, legitimate cost
inverse, and the existing first-part recovery limit. The legacy single-lot
conversion path also needs explicit admission and economic transfer; it currently
delegates around the SKU group hooks. No claim is made that it already works.

The next concrete gate is later cost recost after an economic transfer to a
second SKU. Native currently posts source cost and physical transfer journals;
the prepared cost projection alone does not prove that all economic custody
scopes receive the corresponding source entries. That chain must be checked and
repaired before this prepared layer can be installed in the owning candidate.
