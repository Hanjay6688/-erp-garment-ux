# Fourteen real Auth/HTTP qualifications

Expected cases and boundaries are declared in EXPECTED.json before runtime.
Run only in the disposable CP6 runtime prepared by
`.github/workflows/cp7-ow04-http.yml`:

```sh
python ../auditor/scripts/ow04-qualification/transport_probe.py
```

The entry accepts no arguments or authority overrides. Its normal repo root
is derived from this tracked path; for source-only imports from elsewhere set
ERP_REPO explicitly. Before opening a DB connection it requires the exact
Native63-qualified core/probe/dependencies bound by QUALIFIED_CORE.json.
The binding must cite a completed successful Native workflow, all 63 exact
cases, restoration/advisors and all five package gates. A pending candidate
or the historical Native58 receipt cannot qualify this entry.
The current HTTP candidate and its actual case/entry/declaration hashes are
recorded separately from the reused Native candidate/run/job.

The harness creates real Auth users, uses actual password-grant tokens and
PostgREST, and tests real COMMIT followed by fresh-connection money, original
payment, journal/date-pair, stock and HPP assertions. Replays/refusals require
the complete private table inventory and exact full rows to stay unchanged.
No request issues a test-minted token or replaces a Native authority guard.
Administrative stock/sale/payment/period/master fixtures are labelled and
confined to the copied database; normal writers post their source documents.

The original eight settlement cases and EXPECTED.json remain unchanged.
SOURCE_HTTP_EXPECTED.json declares six additional actual Auth cases: return
inverse, payment inverse, zero-difference inverse, revoked authority, an actual
refund dependency, and changed intent on a cached request. The first three
also replay the actual committed response and demand no further effects.
The negative dependency case requires exactly the six source/event/journal
identifiers from the actual consumption, including absence of extra rows.

PASS requires all fourteen exact IDs, real Auth cleanup, copied-database removal,
CP6 restoration and advisor gate. Preserve the first complete job log and
CP7_OW04_HTTP.json even on failure. Source preflight and counter records live
in `docs/cp7/d17-14/ow04/http-check/`; they are not HTTP runtime results.
This does not prove browser interactions, concurrency, interrupted-response
recovery, all corrected sources/cohorts/APPLY, or production readiness.

Six separately declared public-SQL races now follow this group in the same
disposable workflow, using RACE_EXPECTED.json and race_probe.py. They reuse
the unchanged qualified backend, not this HTTP group's results:

```sh
python ../auditor/scripts/ow04-qualification/race_probe.py
```

Each race gets a fresh copied database. The test requires observed exact
holder-to-worker blocking and checks the full ledger and unchanged financial,
date, stock and HPP oracles. The termination case only kills its own known
holder PID after proving the exact disposable race database; it tests server
rollback of an uncommitted transaction. Real Auth belongs to the first group;
SQL fixture claims do not establish Auth, browser or lost-committed-reply proof.

The same race entry also runs two separately declared source-inverse cases on
fresh copies: concurrent identical request UUIDs must return one identical
committed outcome; distinct UUIDs with the same stale review must yield exactly
`P0001 CP7_SALES_REVIEW_CHANGED` for the loser and no additional effects. Both
require one source inverse, one ADJ−200 and one source operation/completion,
with unchanged signed Native money/date/stock/HPP assertions. The old six-case
group remains distinct; the final gate requires that group plus the two new
IDs, complete cleanup and their exact declaration/implementation hashes.
The literal source-race declaration retains candidate978 as proposal-source
provenance. Runtime eligibility comes from the same actual Native63 receipt
gate as HTTP, not that old provenance value. Separate adapter experiments
are archived only and are not installed or imported.

The four browser cases remain a separate workflow and test initial settlement
through the exact active UI source manifest, with the original escrow retained
as provenance. They do not become source-inverse browser proof
when the backend changes. Runtime receipts record the candidate and reused
Native identity separately; pure registration/binding controls are not runtime
evidence. The old qualification binding stays intact until Native63 actually
passes; preparation alone never authorizes rebinding it.
